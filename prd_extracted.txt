1. Overview
This PRD defines the scope, requirements, and technical specifications for the Authentication and Role-Based Access Control (RBAC) module of the Multi-Tenant E-Commerce SaaS Platform being developed during the Zaalima Development Internship.
This module is the security foundation of the entire platform. Every other module (Store Management, Inventory, Payments, Analytics) depends on the identity and permission layer built here. Weak authentication or incorrect role assignment will compromise the entire system.
2. Objectives
Implement a secure, stateless authentication system using JSON Web Tokens (JWT).
Enforce strict Role-Based Access Control (RBAC) separating three distinct user roles: Super Admin, Vendor, and Customer.
Provide secure registration and login workflows tailored to each role.
Protect all sensitive API routes with middleware-level authorization checks.
Ensure passwords are stored securely using Bcrypt.js hashing.
Set up HTTP security headers via Helmet.js to harden the Express server.
3. User Roles & Permissions
The platform operates with three distinct roles. Each role has a unique registration path, login mechanism, and set of authorized actions.
3.1 Super Admin
A single, pre-seeded platform-level administrator. Super Admin accounts are NOT publicly registerable — they are created via a secure database seed script. The Super Admin has unrestricted access to all platform resources.
Permissions:
Approve or reject Vendor registration applications.
Suspend or permanently ban Vendor or Customer accounts.
Access full platform analytics (revenue, order volume, active stores).
Manage platform-wide configurations and settings.
View all stores, products, and orders across all tenants.
3.2 Vendor
A registered business owner who applies for a Vendor account. Vendor registration requires admin approval before the account is activated. Vendors have isolated access limited to their own store data.
Permissions:
Register via the Vendor Registration form (pending approval state).
Login and access their dedicated Vendor Dashboard after approval.
Create, update, and delete products within their own store.
View and process orders belonging to their store only.
Upload product images via Cloudinary integration.
View store-specific analytics.
3.3 Customer
An end-user who registers to browse products and place orders. Customer registration is instant with no approval required.
Permissions:
Register and login via the Customer portal.
Browse all active vendor stores and product listings.
Add products to cart and complete checkout.
View their own order history and profile.
Cannot access any Vendor or Admin routes.
4. Pages & Screens (Frontend)
4.1 Customer Registration Page  —  /register
Form fields: Full Name, Email Address, Password, Confirm Password.
Client-side validation: email format, password minimum 8 characters, password match confirmation.
On submit: POST /api/auth/register with role: 'customer' in the request body.
On success: redirect to Customer Login page with success toast notification.
On failure: display inline error messages returned from API (e.g., 'Email already in use').
4.2 Vendor Registration Page  —  /vendor/register
Form fields: Business Name, Owner Full Name, Email Address, Password, Confirm Password, Business Description (optional).
Client-side validation: same as Customer plus business name required.
On submit: POST /api/auth/vendor/register — account created with status: 'pending'.
On success: display informational message: 'Your application is under review. You will be notified via email upon approval.'
Vendor cannot log in until status is changed to 'active' by Super Admin.
4.3 Login Page  —  /login
Shared login page for Customers and Vendors (role detected server-side from JWT payload).
Form fields: Email Address, Password.
On submit: POST /api/auth/login.
On success: store JWT in localStorage (or httpOnly cookie — see Section 6), redirect based on role:
role: 'customer'  →  redirect to /shop (Customer storefront).
role: 'vendor'  →  redirect to /vendor/dashboard.
role: 'superadmin'  →  redirect to /admin/dashboard.
On failure: display error toast — 'Invalid email or password.' or 'Account pending approval.'
Include a link: 'Register as a Vendor' and 'Register as a Customer'.
4.4 Admin Login Page  —  /admin/login
Separate, non-publicly-linked login page for Super Admin.
Form fields: Email Address, Password.
Same flow as /login but restricted — only accounts with role: 'superadmin' are accepted.
Any non-admin login attempt returns 403 Forbidden.
4.5 Protected Route Wrapper (React Component)
A ProtectedRoute React component wrapping all authenticated pages.
Reads JWT from storage, decodes the role, and permits or denies rendering.
Unauthenticated users are redirected to /login.
Wrong-role access (e.g. Customer trying to access /vendor/dashboard) redirects to their correct home page.

8. Middleware Architecture
8.1 protect  (Authentication Middleware)
Applied to all routes that require a logged-in user. This middleware must be executed before any role-check middleware.
Reads the Authorization header: Bearer <token>.
If no token: return 401 Unauthorized — 'Access denied. No token provided.'
Verify the token using jwt.verify(token, process.env.JWT_SECRET).
If token is invalid or expired: return 401 — 'Invalid or expired token.'
Attach the decoded payload (id, role, status) to req.user.
Call next() to proceed to the route handler.
8.2 authorizeRoles(...roles)  (Authorization Middleware)
A factory function that takes a list of permitted roles and returns an Express middleware. Used after protect.
Check if req.user.role is included in the roles array.
If not: return 403 Forbidden — 'You do not have permission to access this resource.'
If yes: call next().
Usage example:
router.get('/admin/analytics', protect, authorizeRoles('superadmin'), getAnalytics);
8.3 checkAccountStatus  (Status Middleware)
Used after protect. Ensures the user account is active before granting access.
If req.user.status === 'pending': return 403 — 'Your account is awaiting admin approval.'
If req.user.status === 'suspended': return 403 — 'Your account has been suspended.'
If req.user.status === 'active': call next().
9. Security Requirements
Concern
Implementation
Password Storage
Bcrypt hash with salt rounds of 12. Never store plaintext passwords. Never return password field in API responses.
JWT Secret
Minimum 32-character random string. Stored in .env file only. Never committed to GitHub.
Token Expiry
JWT expiry set to 7d for Customer, 1d for Vendor and Admin. Implement token refresh if time permits.
HTTP Headers
Helmet.js applied globally on the Express app. Enables XSS protection, Content-Security-Policy, HSTS, and removes X-Powered-By.
Input Validation
express-validator on all auth endpoints. Sanitize emails, check password length, reject unexpected fields.
Rate Limiting
Apply express-rate-limit to /api/auth/login — max 10 requests per 15 minutes per IP to prevent brute force.
CORS
Configure cors() middleware to allow only the frontend origin. Restrict methods to GET, POST, PATCH.
MongoDB Injection
Use Mongoose schema validation. Never pass raw user input directly into MongoDB queries.

11. Acceptance Criteria
All items below must be passing before the module is considered complete and ready for handoff to other team members.
A Customer can register, log in, and receive a valid JWT with role: 'customer'.
A Vendor can register and receives a 'pending' status. They cannot log in until approved.
Super Admin can log in from /admin/login and receives role: 'superadmin' in the JWT.
Super Admin can approve a Vendor via PATCH /api/admin/vendors/:id/approve. Vendor can then log in successfully.
All protected API routes return 401 if no token is present.
All role-restricted routes return 403 if the wrong role attempts access.
Suspended accounts receive a 403 with a clear message on login attempt.
Passwords are never returned in any API response payload.
Passwords are stored as Bcrypt hashes in MongoDB (verifiable in Atlas).
Helmet.js headers are present in all API responses (verifiable via Postman or browser DevTools).
Login rate limiter blocks requests after 10 failed attempts in 15 minutes.
React ProtectedRoute redirects unauthenticated users to /login.
React role-based redirect sends each role to their correct dashboard after login.
